# Documentation

This project exists to answer one question: **what decisions do I want it to
prove I can make?** So the record is kept as the project is built, not written
up afterwards from memory.

Each phase goes through the same loop:

**Build → Test → Break → Decide → Improve → Document**

| Step | What gets recorded | Where |
|---|---|---|
| Build | What was built in the phase | [JOURNAL.md](JOURNAL.md) |
| Test | Each check that was run, with its date, commit, settings and output | [PROOF.md](PROOF.md) |
| Break | What was broken on purpose and what happened | [PROOF.md](PROOF.md), screenshots in `evidence/` |
| Decide | Each choice, why, and what it costs | [DECISIONS.md](DECISIONS.md) |
| Improve | What a real failure changed | [TROUBLESHOOTING.md](TROUBLESHOOTING.md) |
| Document | The phase in my own words | [JOURNAL.md](JOURNAL.md) |

## Two kinds of document

**The record** is facts. It can be checked against the code, a command's
output or a screenshot.

| Document | Holds |
|---|---|
| [DECISIONS.md](DECISIONS.md) | Every choice made, in order, with its reason and its cost |
| [TROUBLESHOOTING.md](TROUBLESHOOTING.md) | Failures that actually happened: what was seen, the cause, the fix |
| [PROOF.md](PROOF.md) | What the system promises, how each promise is attacked, and the result of every check run |
| `evidence/phase-N/` | Screenshots, terminal output and timings that back a claim |
| [diagrams/](diagrams/README.md) | The architecture diagrams, generated by scripts |
| [guide/](guide/README.md) | The field guide and the Phase 2 workbook |

**The journal** is judgement. [JOURNAL.md](JOURNAL.md) has one entry per
phase, written by me when the phase ends: the problem, why I chose the
approach, what broke, what I changed, and what I would do differently at a
different scale. Nobody else fills it in, and it is not written ahead of the
work.

The final write-up is assembled from both at the end of the project. Until
then there is no case study, no scaling essay and no interview script in this
folder: those are conclusions, and they come last.

## Rules

- **Record a decision when it becomes real in the repository**, not when it is
  first discussed. Add it to the end of DECISIONS.md and never renumber. When
  a later change replaces it, add a **Superseded.** paragraph to the old entry
  saying what replaced it and whether its prediction held.
- **Record a failure only once it has happened and been diagnosed.** A failure
  that was predicted but never seen belongs in the cost of a decision.
- **Every number needs a run behind it.** Add the run to PROOF.md before
  quoting the number anywhere else.
- **Capture evidence at the moment.** A screenshot of a firing alert or a
  scaling graph cannot be recreated later. Save it to `evidence/phase-N/` with
  a name that says what it shows, and link it from the entry it backs.
- **Write the journal entry before starting the next phase**, while the reasons
  are still fresh.

## Templates

### A decision

```markdown
## N. <the choice, stated as a fact>

**Decision.** What was chosen, specifically enough that someone could check
the code for it.

**Why.** The problem it solves, and the alternatives that were rejected and why.

**Cost.** What it makes harder, slower, riskier or more expensive. If this is
empty, the decision is not understood yet.
```

### A failure

```markdown
## N. <what was seen, in one line>

**Seen.** The symptom, with the exact error or numbers.

**Cause.** What was actually wrong, and how it was found.

**Fix.** What changed, where, and how the same test now passes.

**Note.** Optional: what was not affected, or what the failure taught.
```

### A check run

```markdown
### <date>: <check and settings>

Machine: <where it ran>. Commit: <short hash>.

| Assertion | Result |
|---|---|
| ... | ... |

Observations: anything surprising, even if the run passed.
```
