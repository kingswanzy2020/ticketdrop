# Documentation

This project is meant to show the decisions behind a system, not just the tools
in it. The documents follow one loop:

**Build → Test → Break → Decide → Improve → Document**

| Step | What it means here | Where it is recorded |
|---|---|---|
| Build | Nine Go services, a shared platform library, a local stack | The code, and [CASE_STUDY.md § 2](CASE_STUDY.md#2-the-approach-and-why) |
| Test | Unit tests, and two end-to-end checks against the running stack | [PROOF.md](PROOF.md) |
| Break | SIGKILL a service mid-drop, take the payment provider down, kill the scheduler's leader, replay events, send a poison message | [PROOF.md](PROOF.md) |
| Decide | Each choice, why, and what it costs | [DECISIONS.md](DECISIONS.md) |
| Improve | What a failure changed in the code or the design | [TROUBLESHOOTING.md](TROUBLESHOOTING.md), and the "Superseded" notes in DECISIONS |
| Document | The story as a whole, and how it would change with scale | [CASE_STUDY.md](CASE_STUDY.md), [SCALING.md](SCALING.md) |

## The documents

| Document | Read it for |
|---|---|
| [CASE_STUDY.md](CASE_STUDY.md) | The whole story in one place: the problem, the approach and why, what broke, what changed, what is still open, and what comes next |
| [DECISIONS.md](DECISIONS.md) | Every choice made, in order, with its reason and its cost |
| [TROUBLESHOOTING.md](TROUBLESHOOTING.md) | Failures that actually happened: what was seen, the cause, the fix |
| [PROOF.md](PROOF.md) | Each promise the system makes, what could break it, the check that proves it, and the results of real runs |
| [SCALING.md](SCALING.md) | What I would build for a much smaller or much larger crowd, and what would tell me to change |
| [INTERVIEW.md](INTERVIEW.md) | The project told in 30 seconds, in two minutes, and as short stories with links to the evidence |
| [guide/](guide/README.md) | The field guide and the Phase 2 workbook, published as pages |
| [diagrams/](diagrams/) | The architecture diagrams, generated by `diagrams/build.py` |

## Keeping them true

The documents are only worth something if every claim in them can be checked.

- **Record a decision when it becomes real in the repository**, not when it is
  first discussed. Add it to the end of DECISIONS.md; never renumber. When a
  later change replaces it, add a **Superseded.** paragraph to the old entry
  saying what replaced it and whether its prediction held.
- **Record a failure only once it has actually happened and been diagnosed.**
  A failure that was predicted but never seen belongs in the cost of a
  decision, not in TROUBLESHOOTING.md.
- **Every number needs a run behind it.** Add the run to the results in
  PROOF.md, with the date, the settings and the output, before quoting the
  number anywhere else.
- **Say what is not done.** A known gap belongs in the cost of its decision and
  in the gaps table in CASE_STUDY.md.

### Template: a decision

```markdown
## N. <the choice, stated as a fact>

**Decision.** What was chosen, specifically enough that someone could check
the code for it.

**Why.** The problem it solves, and the alternatives that were rejected and why.

**Cost.** What it makes harder, slower, riskier or more expensive. If this is
empty, the decision is not understood yet.
```

### Template: a failure

```markdown
## N. <what was seen, in one line>

**Seen.** The symptom, with the exact error or numbers.

**Cause.** What was actually wrong, and how it was found.

**Fix.** What changed, where, and how the same test now passes.

**Note.** Optional: what was not affected, or what the failure taught.
```

### Template: a check run

```markdown
### <date>: <check and settings>

Machine: <where it ran>. Commit: <short hash>.

| Assertion | Result |
|---|---|
| ... | ... |

Observations: anything surprising, even if the run passed.
```
