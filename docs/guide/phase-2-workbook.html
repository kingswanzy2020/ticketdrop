Phase 2 workbook · your part · updated 3 October 2026

Into Kubernetes, on your laptop

The services already run under docker compose. In this phase you move them into a real Kubernetes cluster on Docker Desktop, and you write every file yourself.

  • Cluster: docker-desktop
  • Your files go in ticketdrop-gitops/
  • AWS cost: none
  • 0 of 10 steps ticked
The picture

From a folding table to a real venue

Docker compose is a folding table at a market: you set everything out by hand, and it works because you are standing there. Kubernetes is a venue with a manager. You hand over a written description of what should be running, and the manager keeps it that way: restarts what dies, sends customers only to staff who are ready, and calls in more staff when the queue grows.

Your work in this phase is writing that description. Nothing about the services changes.

The work

Ten steps, in order

Tick a step when its "done when" check passes. Ticks are remembered in this browser only.

Do
In Docker Desktop: enable Kubernetes, and raise memory from 8 GB to about 12 GB. Create the folder ticketdrop-gitops/ beside ticketdrop/ and run git init in it.
Why
Everything below runs here. 8 GB is tight for a database operator, an ingress controller, KEDA and nine services together.
Watch for
Your only kube context today points at an EKS cluster that no longer exists. Make sure the new one is selected before any kubectl apply.
Done when
kubectl config current-context prints docker-desktop and kubectl get nodes shows Ready.
Do
Create the namespaces ticketdrop and data. Label ticketdrop so Pod Security Admission enforces the restricted standard.
Why
A namespace is a room with its own rules. With restricted enforced, a pod that asks to run as root is refused at the door, so a mistake in your chart shows up now and not in an audit.
Watch for
Do not enforce restricted on data yet. Check what the database operator's pods need first.
Done when
kubectl run test --image=nginx -n ticketdrop is rejected with a Pod Security message.
Do
Build the nine images with a tag that is not latest, for example dev. Decide the pull policy your chart will use locally.
Why
There is no registry yet. Docker Desktop's cluster can use images from the local store when the containerd image store is on, which it is on your machine.
Watch for
With the tag latest, Kubernetes always tries to pull from a registry and fails. ErrImagePull on a local image nearly always means the tag or the pull policy.
Done when
A throwaway pod using ticketdrop/gateway:dev gets past image pull. It will then crash for lack of settings, which is expected.
Do
Run goaws in data: a ConfigMap holding goaws.yaml, a Deployment mounting it at /app/conf/goaws.yaml, and a Service on port 4100.
Why
It stands in for SNS and SQS until Phase 4. It is also your first complete workload: config, pod, stable address.
Watch for
The file's Host value and every service's EVENTS_QUEUE_URL must use the Service's in-cluster name, such as goaws.data.svc.cluster.local. It keeps its queues in memory, so a restart empties them.
Done when
From a port-forward, aws --endpoint-url http://localhost:4100 sqs list-queues lists ten queues: five, each with its dead-letter queue.
Do
Install the CloudNativePG operator. Declare one small Postgres cluster in data with six databases (catalog, orders, inventory, payments, fulfillment, scheduler), each with its own user. Each service gets a Secret holding its DATABASE_URL.
Why
An operator is a controller that knows how to run one piece of software. You describe "a Postgres like this" and it handles startup, storage and failover. You have already run Postgres as a bare StatefulSet; this is the next level.
Watch for
A design choice that is yours to make and record: one Postgres cluster with six databases, or six clusters. One is lighter on memory and matches local compose; six isolates better. Read the operator's current docs for how it declares extra databases and roles before you commit.
Done when
psql through a port-forward, using one service's own user, can reach its database and is refused on another's.
Do
Write charts/service/, one chart that any of the services can use, and a values file for orders. It needs a Deployment, a Service with both ports, a ServiceAccount, and environment from values plus the database Secret.
Why
Nine near-identical sets of YAML would drift apart. One chart means a fix to probes or security lands everywhere at once, and each service costs one values file.
Watch for
  • All three probes go to port 9090. Liveness uses /healthz, readiness /readyz.
  • The startup probe must allow for the 60-second database wait plus migrations, or Kubernetes kills the pod while it is still patiently waiting.
  • terminationGracePeriodSeconds must exceed SHUTDOWN_DELAY + SHUTDOWN_TIMEOUT. Set SHUTDOWN_DELAY to a few seconds here: it covers the moment between readiness going false and traffic actually stopping.
  • Security context: non-root, read-only root filesystem, no privilege escalation, all capabilities dropped, seccomp RuntimeDefault. The namespace from step 2 will reject the pod otherwise.
  • Give every container resource requests. Karpenter will later size nodes from them.
Done when
helm lint is clean, the orders pod is Ready, and kubectl delete pod on it logs the shutdown steps in order and exits 0.
Do
Add values files for web, gateway, catalog, inventory, payments, fulfillment, notifications and scheduler. Add a PodDisruptionBudget and topology spread to the chart. Run two replicas of the HTTP services.
Why
This is the test of your chart: if a service needs a template change and not just values, the chart was not general enough. The disruption budget tells Kubernetes how many pods it may take away at once during maintenance.
Watch for
payments and fulfillment serve no app traffic, so their Service matters only for metrics. gateway has no database and no queue; the chart must cope with both being absent. web has neither as well, and needs only API_URL. catalog has a database and the topic but no queue. notifications is the reverse: a queue and no database. scheduler is the odd one: no app port, no events at all, but it needs its database, and it should run two replicas, since the point of its leader election is surviving the loss of one.
Done when
All nine are Ready, exactly one scheduler pod reports scheduler_leader 1 on /metrics, and an order ends ticketed. A drop has to exist before it can be ordered: through a kubectl port-forward to catalog, curl -X PUT localhost:<port>/internal/v1/drops/first -d '{"name":"First","venue":"Here","opens_at":"2026-01-01T00:00:00Z","tiers":[{"tier":"general","price_cents":2500,"capacity":100}]}'. An opening time in the past makes the scheduler open it within a second. Then order it through a port-forward to the gateway, or open a port-forward to web in a browser and buy a ticket there.
Do
Install Traefik with its Gateway API provider on. Write a Gateway and two HTTPRoutes: /v1 goes to the gateway service, and everything else goes to web.
Why
Port-forward is a back door for you. A Gateway is the real entrance. The same two objects, with a hostname and a certificate added, are what you will use on EKS.
Watch for
Port 8080 is already taken on your machine, so choose another for Traefik's listener. A route in one namespace attaching to a Gateway in another has to be allowed by the Gateway. Confirm in the current Traefik chart docs how the Gateway API CRDs get installed.
Done when
curl http://localhost:<port>/v1/drops/x/availability is answered by the app (a JSON 404 from inventory), http://localhost:<port>/ in a browser shows the shopfront, and /v1/healthz through the same address is a 404 from the gateway: the admin port is not exposed.
Do
Add NetworkPolicies: deny everything in ticketdrop by default, then allow only what the diagram shows. Traefik to web and to gateway; web to gateway; gateway to catalog, orders and inventory; orders to inventory; scheduler to catalog and inventory; services to Postgres, goaws and DNS.
Why
By default every pod can call every other pod. If the gateway were ever compromised, it could talk straight to the payments database. A default-deny policy means each connection exists because you wrote it down.
Watch for
Forgetting DNS is the classic mistake: everything breaks and nothing says why. Also, it is not yet confirmed that Docker Desktop's cluster enforces NetworkPolicy at all. Test that first; if it does not, write the policies anyway and prove them on EKS.
Done when
A test pod in ticketdrop cannot reach Postgres, while orders still can, and an order still completes.
Do
Install KEDA. Write a ScaledObject for fulfillment using the SQS scaler pointed at goaws, from 0 replicas up to a small maximum.
Why
CPU tells you a pod is busy. Queue depth tells you work is waiting, which is what matters for a consumer. With nothing waiting, zero pods run and cost nothing.
Watch for
The scaler needs an endpoint override and credentials to reach an emulator instead of AWS; check the current KEDA docs for the exact field names. Decide what "enough backlog for one more pod" is and write down why: fulfillment handles about 20 orders a second per pod.
Done when
With the queue empty there are no fulfillment pods. Placing a few hundred orders brings several up, and they go away again after the queue drains.
The exit

Phase 2 is finished when

  1. A drop of more orders than tickets, sent through the Traefik Gateway, ends with no oversold ticket and no order left pending.
  2. Fulfillment went from 0 pods to several and back to 0 without you touching it.
  3. Deleting a pod mid-drop loses nothing.
  4. Everything in the cluster was created from files in ticketdrop-gitops/, and you can delete the namespaces and bring it all back from those files.
  5. Each choice you made is in docs/DECISIONS.md, and each thing that really broke is in docs/TROUBLESHOOTING.md.
