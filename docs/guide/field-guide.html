TicketDrop

A ticket-selling platform made of small Go services, built to run on Amazon EKS. It exists to practise, and to prove, the work of a DevOps engineer: packaging, deploying, scaling, securing and observing a real system.

The idea

A box office that opens at 10:00 sharp

Picture tickets for a big concert going on sale at 10:00. At 9:59 nobody is buying. At 10:00 ten thousand people press Buy in the same second, and there are only a thousand tickets. That moment is called a drop.

A drop is hard on a system in two ways. It must never sell the same ticket twice, however many people click at once. And it needs far more computing power for ten minutes than for the rest of the day, so it has to grow quickly and shrink again, or you pay for idle machines.

Those two problems are why this project is about tickets and not a shop. Both give a result you can measure: zero oversold tickets, and how many seconds it took to scale.

How it works today

The journey of one order

Think of the services as staff at the box office, each with one job. They do not shout across the room at each other. They pass notes through a shared pigeonhole, and each person has their own tray.

our services network edge messaging data, success cluster controllers Git and CI failure
  1. The doors open on time. The scheduler is the caretaker with the clock. At the drop's opening time it tells catalog, catalog announces drop.opened, and inventory puts the tickets on the rack. An order placed a moment early is turned away, because the rack is still empty.
  2. The shopfront is what the customer sees. It is a web page, and it asks the gateway for everything it shows, like any other client would.
  3. The gateway is the front door. It lets in only the requests on its list and turns everything else away.
  4. Orders takes your order and, while you wait, asks inventory to set your tickets aside. If none are left you hear "sold out" straight away.
  5. Inventory guards the ticket rack. Taking tickets is a single database update, and the database itself refuses to let the count go below zero.
  6. From here nobody waits on anybody. Orders drops a note, order.created, in the pigeonhole. Payments picks it up and charges the card.
  7. If the card works, inventory makes the hold permanent and fulfillment issues the tickets. If the card is declined, inventory puts the tickets back and the order is marked failed.
  8. If no answer about the payment comes at all, the tickets are not kept for ever. A hold lasts ten minutes. When it runs out, inventory puts the tickets back, says so with hold.expired, and the order is marked failed. Payments will not charge an order whose hold has run out.
  9. The customer is told. When the order ends, either way, orders drops one last note saying how. Notifications picks it up and sends the customer a message.
  10. A note nobody can read, after three tries, goes to a separate tray called the dead-letter queue, where a person can look at it. It never blocks the line.

Where it is heading

The finished platform on AWS

What happens when a drop opens

Two controllers work as a pair. KEDA looks at how many messages are waiting and decides how many pods are needed. Karpenter notices pods that have nowhere to run and adds machines. KEDA is the manager calling in more staff; Karpenter is the one finding them desks.

Phase 2 proves the KEDA half on your laptop. Karpenter needs real AWS and arrives in Phase 5.

Decisions

What has been decided, and what each choice costs

Every choice buys something and costs something. The full text of each is in docs/DECISIONS.md.

#DecisionWhyWhat it costs
1Ticket drops, not a shopA real burst of load, and a pass-or-fail result: no ticket sold twice.Holding and releasing tickets must be correct under pressure.
2One Go module with a shared platform libraryA probe or a metric means the same thing in every service.A change to the library rebuilds every service.
3Each service owns its databaseA service can change and deploy without asking the others.No query can join across services.
4One SNS topic, one SQS queue per consumerA slow consumer backs up only its own queue, and each queue is a scaling signal for one service.More to create and watch. A wrong filter fails silently.
5Events go through a transactional outboxThe order and the note about it are saved together, or not at all.A note can be sent twice, and up to 250 ms late.
6Consumers record the events they handledA note delivered twice does nothing the second time.One extra insert per message; a table to prune later.
7Messages that cannot be handled go to a dead-letter queueDeleting hides a bug; retrying forever blocks the line. An event of a type the service does not expect counts too: it means a subscription is wired wrongly.Each poison message is tried three times first.
8Probes and metrics on a separate port, 9090They can never be reached through the public address.Two ports to declare in every manifest.
9Liveness checks nothing else; readiness doesA database outage must not make Kubernetes restart every pod.A pod that is alive but stuck needs an alert to catch it.
10Shutdown follows a fixed orderWork in flight is finished, then its events are sent.The pod's grace period must be longer than the shutdown.
11Services migrate their own schema at startupNo separate job to run first.Each migration must work with the previous release still running.
12The gateway lists its routes one by oneExposing an endpoint is a deliberate change in one file.A new public route needs a gateway change too.
13goaws as the local SNS/SQS emulatorLocalStack now needs an account and a token. goaws needs neither and was tested first.Exact-match filters only, an unreliable receive count, no S3.
14The first slice skipped payments and inventoryProve the path end to end before building on it.Superseded: both services exist, and the switch was one filter and one constant, as predicted.
15Tickets are held with a direct call before the order is acceptedThe customer hears "sold out" immediately, and nobody is charged for tickets that are gone.Orders cannot be placed while inventory is down. The call has a 2-second limit.
16Stock is one counter per tier, taken with one conditional updateTwo orders racing for the last ticket cannot both win, and the database refuses a count below zero.Every hold for a tier queues on one row. Valkey is left out until a load test shows that matters.
17A declined card and a provider outage are different thingsA decline is an answer and ends the order. An outage is retried, then set aside.An outage longer than a hold loses those sales, though not the tickets.
18An order's final status sticksA late or out-of-order event cannot turn a failed order into a ticketed one.The steps in between are not recorded on the order.
19Catalog owns a drop; inventory learns its tickets when it opensOne place decides how many tickets exist, and an early order is refused with no extra rule.A drop is orderable up to a second after its opening time, and its capacity is fixed once open.
20The scheduler only keeps time, on one replica at a timeServices change their own data. A killed leader needs no cleanup; the standby took over in 5 seconds.A database connection only to hold a lock. Timers pause up to 5 seconds on a failover.
21A hold expires, and nothing is charged after it hasUnpaid tickets return to sale, and a late retry cannot charge for tickets already resold.One rare case is left to a person: a payment that succeeds but arrives after its hold was released.
22Orders announces how each order endedOne note from the service that owns the order says how it turned out, whichever path led there. There is exactly one per order.One more hop before the customer hears, and a customer's email address now travels on the topic.
23Notifications keeps no record, so a message can be sent twiceA repeated email is a nuisance, not a loss, and a record could not prevent it. With nothing to store it can scale from zero.The one exception to "every consumer is safe to repeat". It must be remembered when a real email provider is plugged in.
24The shopfront is rendered on the server and uses only the public APINothing to build, buying works with JavaScript off, and it can do nothing the API does not allow.An extra hop for every page, and each waiting customer asks for news once a second. That load is not measured yet.

What actually broke

Three failures so far

Docker Desktop refused a mount from /tmp

It shares only some folders with its virtual machine. Files mounted into containers now live inside the repository.

The emulator ignored its config file

The image reads /app/conf/goaws.yaml, not the path older examples show. Listing the image's files found it.

Orders stayed pending after a clean stop

Handlers finishing during shutdown wrote events after the sender had stopped. Workers now stop one at a time and the sender goes last.

Words

The vocabulary, in plain terms

OutboxA "to send" tray inside the database. The note is saved with the order, and posted a moment later.
IdempotentDoing it twice has the same effect as doing it once. Pressing a lift button again does not call a second lift.
Dead-letter queueThe tray for notes nobody could deal with, kept for a person to read.
HoldTickets set aside for one order while it is being paid for. It ends one of three ways: confirmed, released, or expired.
Leader electionSeveral copies of a program run, and they agree that only one of them acts. If it dies, another takes over.
Liveness"Is this process alive?" If not, Kubernetes restarts it.
Readiness"Should customers be sent to this one right now?" If not, Kubernetes stops sending traffic but leaves it running.
Visibility timeoutHow long a message is hidden from others while one worker handles it. If the worker never finishes, the message reappears.
ControllerA program in the cluster that keeps comparing what you asked for with what exists, and fixes the difference.
GitOpsThe cluster copies what is in Git. To change the cluster, you change Git.
