The picture

From a folding table to a real venue

Docker compose is a folding table at a market: you set everything out by hand, and it works because you are standing there. Kubernetes is a venue with a manager. You hand over a written description of what should be running, and the manager keeps it that way: restarts what dies, sends customers only to staff who are ready, and calls in more staff when the queue grows.

Your work in this phase is writing that description. Nothing about the services changes.

Starting again

Tearing it down and building it back

Know before you start.

  • Deleting data loses every database. The Postgres volume's reclaim policy is Delete, and entry 29's retain keeps only the CloudNativePG objects, not the data.
  • The passwords survive because they live outside git, in ticketdrop-gitops/secrets/*.password. Lose that folder and scripts/db-secrets.sh makes new ones.
  • Operators remove their own finalizers. An object whose operator has gone, or has lost its rights, keeps its namespace in Terminating forever, and nothing can then be created in it. Deletion order is how you avoid that.
  • Run the commands so they stop at the first failure. A script that runs on prints success over a broken stack (TROUBLESHOOTING entry 6).

The scripts

Three scripts in ticketdrop-gitops/scripts/ follow the orders below. Run them from the repo root:

scripts/teardown.sh          # asks you to type yes; --yes skips the question
scripts/rebuild.sh 2>&1 | tee ../ticketdrop/docs/evidence/phase-2/<name>.txt
scripts/check.sh             # is the stack whole? Run it any time
  • teardown.sh deletes in the order below. It fails if KEDA objects are still there after the uninstalls. If a namespace sticks in Terminating, it prints the reason and stops. At the end it fails if any Helm release, webhook or GatewayClass is left.
  • rebuild.sh first checks that the Helm repos cnpg, kedacore and traefik are added, that the nine ticketdrop/<svc>:dev images exist, and that no namespace is terminating. It then installs in the order below and runs check.sh at the end. It uses helm upgrade --install, so it can safely run again over a stack that is already up.
  • check.sh prints ok or FAIL for each check in step 12 below, and exits non-zero if any fail.
  • All three share lib.sh: the pinned chart versions, the service order, and the guards. Each command is printed as $ … before it runs, each step is timed, and the script stops at the first failure with a FAILED line. Nothing runs unless kubectl points at docker-desktop (set KUBE_CONTEXT to change that).

Tested on 17 November 2026: the teardown took 37s from the full stack, the rebuild 112s with all 16 checks passing, and a second rebuild.sh over the running stack 19s.

Teardown, in this order

  1. Uninstall the nine service releases with helm uninstall <svc> -n ticketdrop --wait, and check that no ScaledObject or TriggerAuthentication is left. Why: KEDA watches only ticketdrop, so its right to edit ScaledObjects comes from a RoleBinding inside ticketdrop. Deleting the namespace first deletes that RoleBinding too, and KEDA can no longer remove finalizer.keda.sh (TROUBLESHOOTING entry 6).
  2. Delete the ticketdrop namespace. Only the Secrets, NetworkPolicies and HTTPRoute are left in it, and none of them has a finalizer.
  3. Delete the data namespace while CloudNativePG is still running. Why: each Database carries cnpg.io/deleteDatabase, which only the operator removes.
  4. Uninstall KEDA, Traefik and CloudNativePG with Helm, then delete their namespaces. Why: Helm also removes their cluster-wide objects (the GatewayClass, the webhooks, the metrics APIService and the ClusterRoles). Deleting only the namespace leaves those behind, and a webhook with no pod behind it can block later API calls.
  5. Check that nothing is left: kubectl get ns shows no Terminating, helm list -A -a is empty, and no webhook or GatewayClass names keda, cnpg or traefik. The CRDs stay on purpose. CloudNativePG keeps its CRDs by resource policy and the Gateway API CRDs are applied separately, so their two Local APIServices also stay.

Rebuild, in this order

  1. Namespaces (platform/namespaces.yaml). Why: everything else lands in one, and each carries its Pod Security level.
  2. Gateway API CRDs (--server-side). Why: Traefik's GatewayClass and the routes need the kinds to exist, and the HTTPRoute CRD is too big for a client-side apply (DECISIONS 42).
  3. CloudNativePG, with --wait. Why: the Cluster, roles and databases are its kinds and are refused until its webhook answers.
  4. goaws, waiting for the rollout. Why: it creates the topic and queues at start, and every consumer reads its queue at start.
  5. scripts/db-secrets.sh. Why: the Cluster's bootstrap reads pg-catalog, each DatabaseRole reads its pg-<svc>, and each service reads its <svc>-db. It needs both data and ticketdrop to exist and not be terminating (TROUBLESHOOTING entry 7).
  6. The Postgres Cluster, waiting for Ready, then roles and databases. Why: roles and databases are applied inside a running cluster. Check that every DatabaseRole shows APPLIED true.
  7. KEDA, with --wait. Why: fulfillment's chart renders a ScaledObject, which is refused until KEDA's CRDs and webhook are there. KEDA also needs ticketdrop to exist, to put its RoleBinding in it.
  8. Traefik, with --wait, then platform/routes/. Why: the Gateway needs Traefik's GatewayClass.
  9. The DNS NetworkPolicy. Why: as in step 9, the allows go in before the deny, so nothing is cut off along the way.
  10. The nine services, in this order: catalog, inventory, orders, payments, fulfillment, notifications, scheduler, gateway, web. Why: each Helm release brings its own NetworkPolicy, so a service's allows exist before default-deny.
  11. default-deny, last. Then wait for every Deployment to be Available.
  12. Check: 14 pods in ticketdrop with fulfillment at 0, the ScaledObject READY True, the Gateway PROGRAMMED True, 11 NetworkPolicies, a JSON 404 from localhost:8088/v1/drops/x/availability and a 200 from localhost:8088/.

If a namespace sticks in Terminating. Read the reason from kubectl get ns <ns> -o yaml (look at status.conditions) and capture it before changing anything. Remove a finalizer by hand only once you know what it would have cleaned up and that it is already gone. For the KEDA pair, that was the HPA.

The picture

A bouncer who checks only the tickets that changed

Until now, "it works" meant you ran the checks on your laptop. CI runs them on GitHub for every pull request, and a ruleset on main refuses the merge until they pass. It never gets an AWS key. It only reads the code, builds it and judges it.

One module holds all nine services, so the Go checks always run on everything. Images are different: each one is built from only go.mod, go.sum, pkg/ and its own services/<name>/. A change to services/orders/ rebuilds one image, not nine.

  • GitOps repo workflow: ticketdrop-gitops/.github/workflows/ci.yaml

How it works

What happens when you open a pull request

The go job and the changes job start together. The build job starts after changes, once for each service in its list, and is skipped when the list is empty. The ci-ok job is the one check the ruleset requires, because the matrix job names change from one PR to the next. It runs even when a job before it failed, and passes only if each one passed, or if build was skipped because there was nothing to build.

The workflow, block by block

  1. on: runs on every pull request, on every push to main, every Monday at 03:23 UTC (a full rebuild and scan of main, so a CVE published after the last merge is found), and by hand. It has no paths: filter. A filtered workflow does not start at all, and a required check that never starts stays "Expected" and blocks the merge for good. Deciding what to build belongs to the changes job.
  2. permissions: contents: read gives the token the right to read the code and nothing else. Every checkout also sets persist-credentials: false, so the token is not left in .git/config where a later step could use it.
  3. concurrency groups a PR's runs by its number, so a new push cancels the run it replaces. Everything else is grouped by commit SHA. A group holds one running and one pending run and a third arrival cancels the pending one, so grouping main by branch would have let a quick third merge cancel the second one's run (DECISIONS 65).
  4. env: holds the tool versions in one place: golangci-lint, govulncheck, and the Trivy image by digest. Every uses: is pinned to a full commit SHA with the tag beside it as a comment. The repo setting sha_pinning_required refuses any other form.
  5. changes checks out with fetch-depth: 0, because a shallow clone has no base commit to diff against. On a PR it compares the PR's base with its head. On a push it compares github.event.before with the new commit. The a && b || c expression is the workflow's way of writing "if PR then b else c". Both commits reach the script through env:, never pasted into the shell line, so text from GitHub cannot become a command. The script's one line of JSON becomes the job's services output and is written to the run's summary.
  6. go reads the Go version from go.mod (so CI and your laptop agree), then runs:
    • make vet, which is go vet plus the gofmt check;
    • golangci-lint with .golangci.yml;
    • go test -race;
    • govulncheck, which reports a vulnerability only when your code can actually reach the affected function.
    It runs on every change: one module means a pkg/ change can break any service.
  7. build turns the list into a matrix with fromJSON. A matrix over [] is an error, which is why the job carries if: … != '[]'. fail-fast: false lets every service finish, so one failure doesn't hide another. Each job:
    • builds linux/amd64 into a file, image.tar. There is no registry yet, and the docker exporter can hold only one platform.
    • restores the Trivy database (about 1.7 GB), cached once a day.
    • runs Trivy twice: first a HIGH and CRITICAL table for the record, which never fails, then the gate: a CRITICAL with a fix available fails the job.
    • builds linux/amd64,linux/arm64 without pushing, to prove both platforms build. The Dockerfiles compile on the runner's own platform and cross-compile, so no emulator is needed. buildx is pinned to v0.38.2, and build records are not uploaded.
    Each service has its own build cache (scope=<service>), so nine parallel jobs don't overwrite each other's cache.
  8. ci-ok needs the other three and has if: always(). It reads their results as toJSON(needs) through env: and checks them with jq: changes and go must be success, and build success, or skipped only when the list was []. Both rulesets require it from GitHub Actions (app 15368), so no other app can report it.

The script, .github/scripts/changed-services.sh

  1. Which services exist. It lists the directories under services/ at the head commit that contain a Dockerfile. Nothing is hard-coded: a new services/tickets/ is picked up, and a deleted service drops out.
  2. No usable base: build all nine. This covers an empty base, all zeros (GitHub's "before" for a new branch), and a commit the clone doesn't have (possible after a force push). The same applies when the two commits share no history.
  3. The diff. git diff --no-renames --name-only base...head. Three dots mean "what head changed since it left base", so changes that landed on main meanwhile are not blamed on the PR. --no-renames lists a moved file under its old path and its new one, so both services count.
  4. The rules. Any path under pkg/, go.mod, go.sum, .dockerignore or .github/ means all nine; the script prints which file caused that. A path under services/<name>/ adds that service. Anything else adds nothing.
  5. The output is jq -cn '$ARGS.positional' --args …: one sorted line of JSON. With no services left it prints [], never an empty string, because fromJSON('') fails. Messages go to stderr, so only the JSON reaches $GITHUB_OUTPUT.
